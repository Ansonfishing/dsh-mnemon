# v0.3.0: Composable Memory Kernel

[简体中文](../../zh-CN/releases/v0.3.0.md) | **English** | [Extension guide](../extensions.md)

v0.3.0 lifts the existing three-tier system into a composable memory kernel while preserving one-package installation, default behavior, public tools, and existing data formats. Runtime, Documents, and Memory Spaces are independently switchable Layers. The existing routing behavior is expressed by the `default-three-tier` Strategy, and Provider construction is decoupled through a Registry/Factory seam.

## Delivered

- Wire-safe Contracts, `MemoryCatalog`, atomic `MemoryTopologyManager`, `MemoryKernel`, Guards, `MemoryPlan`, and `MemoryReceipt`.
- Separate Catalog, Topology, and Guard generation boundaries. A component or Guard change rejects an old Plan before execution and requires re-planning.
- Independent `off` / `manual` / `automatic` participation for each Layer's `recall`, `write`, `projection`, and `maintenance` channels.
- Model tools and lifecycle activity use an `automatic` trigger. Direct user Web/RPC data-plane operations use `manual`; a tool invocation cannot bypass participation policy.
- `MemoryExtensionHost` and the Cordis `mnemonMemory` service. Extensions may contribute Layers, Adapters, Strategies, and Guards before Host mount or while it is live; unloading advances generations.
- A descriptor-driven Settings UI backed by the `memory-system` RPC endpoint. A discovered Layer needs no fixed frontend enum and starts disabled and manual-only.
- Strategy manifests, permission boundaries, and deterministic replay primitives as the artifact interface for future model-generated shadow/canary/rollback workflows.
- Multiple private source workspaces while npm still publishes one `dsh-mnemon` package, with new `contracts`, `kernel`, `extension-sdk`, `provider-sdk`, `strategy-sdk`, default Layer, and default Strategy subpaths.

## DSH 0.1.1-rc.2 compatibility and multimodal support

- Every direct `@deepseek-ai/dsh*` development dependency is pinned to 0.1.1-rc.2. The lockfile matches the official rc.2 dependency graph, which intentionally retains rc.1 for unchanged internal packages and contains no older DSH prerelease line. The published UI-primitives peer range continues accepting compatible 0.1.0-rc.6 consumers and the 0.1.1 prerelease line beginning with rc.1, including rc.2.
- The published plugin retains its Node.js 20 engine floor for older compatible DSH hosts. The DSH rc.2 combination requires `^22.19.0 || >=24.0.0`, matching the upstream repository: a Node 20 Headless probe fails before dsh-mnemon loads because the host imports the Node Zstd API and uses `Promise.withResolvers`. This conditional host requirement cannot be repaired inside a plugin.
- Existing Client and subagent integrations type-check against rc.2 without an API shim. The model catalog now preserves DSH's merge-extensible `inputModalities`, and Settings labels image-capable routes as **Image input**.
- The first-party multimodal route available in this DSH line is `deepseek-official/deepseek-v4-flash-vision-exp` (`DeepSeek-V4-Flash-Vision-Exp`, text + image). DSH rc.2 is published on npm's `latest` and `next` tags; pin `@deepseek-ai/dsh@0.1.1-rc.2` for a reproducible installation.
- Upstream rc.2 prioritizes reusable DeepSeek Files API uploads and normalizes image size and format for the selected model. Mnemon continues to preserve DSH-owned attachment references instead of copying image bytes into its own storage.
- Lifecycle processing accepts DSH's durable image attachment references, preserves every original multimodal content block when appending guidance, and counts only text toward activity thresholds. It never persists raw image bytes into Mnemon storage.
- Mnemon's background AI metadata, Agent Query, distillation, smart-selection, and Document-archive prompts remain text-only. Selecting a vision route is supported as a complete model route but does not silently add image ingestion to those jobs.

No dsh-mnemon data migration is required for this compatibility update. The optional DSH SQLite session backend is separate: rc.2 uses schema 17 and still rejects older schemas without migration; shipped profiles do not select it.

## Upgrade and data compatibility

Upgrading from v0.2.13 requires no data migration. Runtime JSON/Markdown, Documents, the Memory Space registry, Provider service registry, Mnemon Native Stores, and remote Provider data formats are unchanged.

Without `memoryTopology` configuration, resolution produces a topology equivalent to the old behavior: all three Layers enabled, all four participation channels `automatic`, and `default-three-tier` selected. Existing `storageScope`, `dataDir`, Provider, recall-quality, lifecycle, tool, and UI settings continue to apply.

Recommended upgrade sequence:

1. Verify Node.js is `^22.19.0 || >=24.0.0` before installing DSH 0.1.1-rc.2.
2. Back up the current Mnemon root or export a Mnemon Pack using the existing procedure.
3. Update `dsh-mnemon` and restart every DSH profile that uses it.
4. Confirm the three default Layers under **Settings → Memory System → Layer topology**.
5. Inspect Catalog/Topology generations and Providers on **Status**.
6. Validate a direct Web/RPC read through the `manual` path, then a conversation tool through each required `automatic` path.

`enabled=false` stops participation without deleting or moving data. Re-enabling uses the same directories. Before downgrading to v0.2.13, back up and remove extension-only Layer / Strategy configuration from YAML. No persistent format changed, so package rollback needs no reverse data migration.

## Extension-author migration

- Import only public `dsh-mnemon/*` subpaths, never repository-internal `src/` or `packages/` paths.
- Let the disposer returned by `mnemonMemory.register()` own component lifetime; do not maintain a second process-global Catalog.
- Keep Strategies to JSON-safe step proposals with no data-plane handles. Wrap permissions in a manifest and replay disabled-Layer, automatic/manual, budget, and escape cases.
- Honor `AbortSignal` in executors and let the Kernel produce `succeeded`, `partial`, `failed`, or `cancelled` Receipts.
- Re-plan after a stale-plan error instead of replaying old steps.

The repository's old `src/memory-system/*` files are source-compatibility facades only. Third parties should use npm subpaths.

## Security boundaries and current limits

- Guards may only deny. A Strategy cannot broaden Host or participation authority, and a changed Guard set invalidates old Plans.
- A Cordis isolate owns scope and unloading; it does not sandbox malicious JavaScript. Layer executors, Provider Adapters, and Strategies must come from trusted packages.
- This release does not automatically execute newly model-generated code. It delivers manifests, permission wrapping, replay, and authoritative Kernel validation.
- Any new engine can integrate today as an independent Layer/Adapter. Fully dynamic Memory Space Provider settings cards, connection schemas, and persistent-registry registration are not generalized yet; the nine current Providers remain in the built-in Catalog.
- Existing controller data planes remain compatible and are uniformly subject to Layer participation gates. Moving every legacy path onto persisted Plan/Receipt execution is an incremental follow-up with no change to this release's public behavior.
